# Аудит операций перед авторитетными клиентскими командами

**Состояние аудита:** начат; это перечень и предварительная классификация, не доказательство полного покрытия всех обходных путей и не утверждение о проверке безопасности сети. Основан на коде ветки после `52835fd`. Подробные требования и критерии: [спецификация](client-authoritative-edits-spec.md), задачи 0.3 и 1.1–1.5.

Обозначения: **G** — общий игровой state/контекст; **H** — история/журналы; **P** — локальная презентация/предпочтения; **N** — существующая сетевая операция, отдельно требующая проверки; **B** — временно блокируется клиенту/зрителю; **D** — решение о допустимых правах и условиях ещё требуется. Имена ниже — фактические публичные entry points. Их группировка не означает, что реализация находится на стороне хоста или что существуют команды для клиента.

### Проверка существующих правил экипировки и локальной передачи

- `equipItem` отклоняет ровно строку прочности `0%`, для двуручного предмета в руке занимает оба слота и при вытеснении двуручного очищает обе руки; затем сбрасывает `contentsPath` и менеджер пересчитывает вес/характеристики. Снятие очищает все слоты с данным ID. При отказе helper возвращает старый объект; менеджер теперь не пересчитывает его в месте (`scripts/equip-broken-state-immutability.test.mjs`).
- Выбор совместимого слота и запрет сломанного предмета в обычном UI выполняются в `InventoryScreen`/`InventoryManagerUI`, а сам helper не проверяет принадлежность предмета, уникальность ID или совместимость `equipmentSlot`; NPC helper также не проверяет прочность. Поэтому эти функции нельзя принимать за валидацию будущей сетевой команды.
- Локальная передача игрок↔NPC в `transferItemBetweenCharacters` — отдельный механизм от GM `inventoryTransfers`. Она ограничивает запрошенное количество размером стека; теперь нецелые, неположительные и неконечные количества и передачу в тот же тип владельца отклоняет без изменения обоих инвентарей (`scripts/local-companion-transfer-invalid.test.mjs`). В `handleTransferItem` есть отдельная UI-проверка критического веса NPC при передаче ему, но сам helper не проверяет вес/согласие; не распространять её автоматически на GM `inventoryTransfers`. Локальная передача больше не объединяет разные предметы только по имени: слияние допускается лишь при совпадении остальных сериализованных свойств, полном ресурсе и отсутствии sentient/container (`scripts/local-companion-transfer-stack.test.mjs`); при частичной передаче использованная единица остаётся в исходном стеке, как при split/GM transfer. Правила контейнеров, экипированных и sentient-предметов между этими механизмами различаются и нуждаются в отдельном согласовании до включения клиентской команды.

## Существующие сетевые входы и известные открытые риски

- `turn_result_from_player` проверяет `HostTurnAuthority`, соединение/активного игрока и ревизию; оба host-обработчика дополнительно отклоняют заявленную роль spectator/отсутствующую роль до принятия (`scripts/host-turn-connection-role.test.mjs`, контролируемый тест извлечённых callbacks). Роль находится в metadata соединения, поступающей от клиента, и не является аутентификацией или самостоятельной границей безопасности. Путь по-прежнему передаёт хосту клиентский `saveFile` для восстановления. Это существующий путь результата ГМ, не утверждение о валидации каждого поля или границе безопасности против изменённого клиента. Требуется отдельный аудит и контракт полномочий.
- `new_player_character_data` и четыре co-op сообщения обрабатываются отдельно от нового командного протокола. Входящий персонаж теперь проверяется на соответствие активному соединению и роли, но его поля целиком ещё не валидируются. В четырёх co-op сообщениях хост теперь сопоставляет senderId с актуальным соединением и единственным персонажем игрока; инициатор берётся из хостового состояния, участники и содержимое проверяются, а активная заявка не перезаписывается. Оба host-пути и заменённое соединение проверяются контролируемыми handler-тестами (`scripts/coop-network-identity.test.mjs`). Явно отклонённые при приёме запросы (включая host restore) по возможности возвращают отдельное предупреждение клиенту, без утверждения о других операциях. Это не протокол с revision/ACK: потерю ответа, отказ после планирования React, порядок и повторы ещё необходимо обработать и проверить в браузере; старые клиенты не показывают новый отказ.
- Входящие сообщения от закрытого или заменённого соединения теперь отбрасываются; `scripts/obsolete-peer-message.test.mjs` моделирует все три обработчика. Это не заменяет полную проверку содержимого разрешённых сообщений.
- Задержанный release `HostTurnAuthority.beginMutation()` из старой сессии ранее мог снять hold новой сессии после `reset`; добавлена проверка поколения (`scripts/network-turn-protocol.test.mjs`).
- `full_sync`, `turn_result_ack`, `request_full_sync`, `chat_message` используют отдельную семантику доставки; новый command ACK нельзя считать эквивалентом подтверждённого React commit. Нужны тесты reorder, дублей и неопределённого исхода.

## Дополнительные вопросы к commit-барьеру

`restoreFromSaveData` планирует отдельные React-обновления настроек, инструкций, карты, посещённых локаций, мира и номера хода. Реальный React DOM с JSDOM (`scripts/react-snapshot-context-commit.test.mjs`) показывает, что срочный commit state может произойти до transition-обновлений контекста; прежняя проверка не различала такой случай. Host/client барьеры теперь сравнивают все перечисленные общие поля и выполняются повторно при их обновлении; локальные настройки исключены из сравнения. Ожидаемый контекст отделён от изменяемого `gameContextRef`, чтобы effect не мог подменить ожидаемые значения. Тест использует production comparator с React harness и проверяет wiring hook по исходнику, но **не** является тестом полного `useGameLogic` или двух браузерных peers; соответствующая сквозная проверка остаётся необходимой.

## Изменения объектов карты по ссылке

`forgetLocation` изменял `adjacencyMap` вложенного объекта старой карты через поверхностную копию, из-за чего ранее опубликованное состояние изменялось до commit; теперь изменённые локации копируются (`scripts/forget-location-immutability.test.mjs`). Отдельно `onRegenerateId` для локации записывает новый ключ напрямую в `gameContextRef.current.worldMap`, оставляя старый ключ и не обновляя все межсущностные ссылки; этот путь пока не подтверждён безопасным и требует отдельного решения для неоднозначных ID, а не автоматического угадывания.

## Общие настройки и инструкции хоста

`updateGameSettings` (общие правила) и `updateSuperInstructions` теперь отзывают полномочия до постановки React-обновления и удерживают их до commit обоих полей; локальные настройки не приобретают hold. Одновременные редактирования, partial commit, no-op и локальное восстановление проверяются на production callbacks/effect в React DOM/JSDOM (`scripts/react-host-shared-context.test.mjs`). Входящий результат хода и выдача snapshot также блокируются при незавершённой gameplay-правке, в том числе после сброса host authority (`scripts/host-shared-settings-guard.test.mjs`). Это не полный тест `useGameLogic` или браузерных peers. Обёртки пользовательских setters мира, карты и посещённых локаций также удерживают authority до commit всех поставленных полей; внутренние setters turn/restore не менялись. `scripts/react-host-shared-context.test.mjs` проверяет частичный commit этих полей и привязку обёрток к менеджеру и двум прямым действиям по исходному коду. Пользовательская очистка game/combat логов также удерживает authority до commit; независимое сообщение кино/музыки в game log не должно блокировать её (`scripts/react-host-shared-context.test.mjs`). При сетевом restore отдельно проверен случай, когда React перебазирует media-сообщение поверх журнала снимка: commit-барьер принимает только зарегистрированный результат сохранения полного исходного журнала (`scripts/react-presentation-log-restore.test.mjs`, React DOM/JSDOM, production callback и comparator). Неизвестные или разрушающие изменения журнала не считаются commit. Это не полная проверка media restore, всех порядков/смен сессии или browser multiplayer. Прочие обходы и изменение вложенных объектов по ссылке требуют дополнительного аудита; зависимости host broadcast effect сами по себе не закрывают окно до commit.

## Приоритет реализации

1. Закончить аудит stage 0/1 и обособить вопросы о правах; подтвердить все entry points и отсутствие побочных записей до блокировки.
2. Спроектировать и проверить контракт version/session/revision/ID/ledger и commit барьер, не снимая guard.
3. Первые поддерживаемые команды — экипировка/снятие; затем устойчивые намерения, конфликты и сверка.
4. Дальше — остальные группы по отдельности; история требует устойчивой идентичности или CAS. Не объявлять всю таблицу реализованной после первой операции.

При совпадении ссылки `gameContextRef.current.playerCharacter` с персонажем ранее опубликованного состояния изменение вложенных полей контекста меняло и старый state. Для auto combat skill, редактирования предмета, удаления пользовательского состояния и удаления/очистки заживших ран теперь создаётся новая оболочка персонажа контекста; регрессия `scripts/shared-character-reference-immutability.test.mjs` проверяет production callbacks на общей ссылке. Семантика отбора ран не изменена. Эти callbacks всё ещё записывают context ref внутри React updater: проверка на общей ссылке не доказывает безопасность отменённого или повторного updater и не является сквозным multiplayer-тестом.

`moveFromStashToInventory` раньше менял вложенные объекты предыдущего снимка, доверял устаревшему объекту из UI (включая вес и свойства), сливал предметы по имени и повторно использовал ID при частичном переносе. Теперь он берет данные из актуального stash, проверяет количество и неоднозначные ID, не сливает стеки, сохраняет ID при полном переносе и создаёт новый при частичном; частично использованная единица остаётся в исходном стеке. Частичный перенос контейнеров и разумных стеков не поддерживается и обозначен в UI (`scripts/stash-take-safety.test.mjs`). Проверка веса по-прежнему использует вес самого предмета и существующий лимит; вес содержимого контейнера и другие stash/drop пути требуют отдельного аудита. Это локальная операция, а не авторитетная сетевая команда; запись context внутри updater остаётся риском.

`dropItem` теперь извлекает свойства из актуального инвентаря по единственному непустому ID; отсутствующий/повторный ID и коллизия с stash отклоняются без удаления предметов (`scripts/drop-stash-integrity.test.mjs`). Ранее можно было записать устаревшие данные UI, удалить несколько предметов с одинаковым ID или удалить предмет при существующей записи stash. В менеджере отказ не запускает пересчёт поверх старого объекта; аналогичная защита добавлена для отклонённых локальных move/split/merge (`scripts/inventory-rejected-actions-immutability.test.mjs`). Отказ из-за legacy ID пока не имеет отдельного сообщения в UI. Содержимое сброшенных контейнеров (хранимое отдельными предметами с путями по именам), удаление из stash и правила самих split/merge по-прежнему требуют отдельной проверки; эти тесты не доказывают их безопасность.

Внутренний setter ранее всегда заменял массивы NPC/фракций непосредственно на полученном объекте состояния, в том числе при no-op, мутируя прежний React snapshot и присланный restore-объект. Теперь фильтрация создаёт новый объект только при наличии некорректных элементов; restore заранее использует то же нормализованное состояние как ожидаемый snapshot барьера (`scripts/internal-state-sanitize-immutability.test.mjs`, controlled тест production callback, и существующие тесты host/client snapshot). Это не полноценный React/browser multiplayer сценарий, а также не исправляет остальные побочные записи внутри updater.

При проверке фактически экспортируемых callbacks обнаружены отдельные реализации `forgetHealedWound`, `clearAllHealedWounds` и `deleteCustomState` в `useGameLogic`: исправление одноимённых менеджеров не защищало эти UI-пути. Теперь и эти callbacks не меняют ранее опубликованного персонажа через общую ссылку с контекстом (`scripts/hook-character-reference-immutability.test.mjs`, извлечённые production callbacks с контролируемым setter). Отбор ран и эффектов не менялся. Запись context ref внутри updater и проверка полного React hook остаются открытыми.
