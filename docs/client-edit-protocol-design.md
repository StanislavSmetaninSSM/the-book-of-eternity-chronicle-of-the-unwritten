# Проект контракта клиентских игровых команд (этап 2)

Это проект и компонентный контракт, **не включение клиентского редактирования**. До сквозной реализации и проверки commit остаётся действующий guard. Протокол применим только обновлёнными сторонами; старые peers не получают запасного пути с локальной правкой или произвольным `SaveFile`.

## Wire и права

Команда v1: `{ version: 1, sessionId, commandId, playerId, base: { version: 1, sessionId, revision }, command }`, где первая группа `command` — `{ type: "equip", itemId, slot }` и `{ type: "unequip", itemId }`. JSON имеет жёсткий лимит 4096 UTF-8 байт; поля строго перечислены, лишние поля, вложенные объекты/массивы вместо ожидаемых, невалидные строки и unsafe revision отклоняются. `commandId` — UUID, генерируемый клиентом до записи намерения. Session ID и идентификаторы ограничены 128 символами; client payload не содержит персонажа, setter, историю или snapshot. Дедупликация сравнивает **всю каноническую команду**, включая сессию, базу, цель и операцию, а не имя предмета.

Хост определяет отправителя по открытому, текущему `DataConnection` в собственной карте соединений; `metadata.role` должна быть player, `connection.peer === playerId`, в хостовом roster — ровно один такой игрок. Зритель, устаревшее/закрытое соединение, отсутствующий/дублированный игрок или подмена ID отклоняются. PeerJS metadata не является криптографической аутентификацией; это разграничение текущей сессии, а не защита от захвата чужого PeerJS ID. Первая поддерживаемая операция — только свой персонаж, в том числе когда он не активен; чужой персонаж/NPC/хранилище не разрешаются. Детальная проверка предмета и слота выполняется хостом на этапе 3 до любого изменения.

## Сессия, сериализация и ledger

Авторитет `HostTurnAuthority` хранит sessionId и последовательную revision. Команда получает базу из последнего **закоммиченного клиентом** host snapshot. На хосте в одном синхронном критическом участке: проверить текущую сессию и соединение; проверить collision/dedupe; проверить busy/restore/turn/gameplay hold и base против последнего выданного grant; зарезервировать новую mutation hold до React setter и сразу занести `pending` в ledger. API компонента возвращает `reserved` только первому вызову (с замороженной копией команды для применения), а повтору — текущий outcome `pending`; повтор нельзя применять заново. Одновременные клиенты не могут принять ту же базу: первый снимает grant/берёт hold, второму возвращается busy или stale. Новый grant не выдаётся до согласованного commit state/history/log/context и освобождения hold. Результат ГМ остаётся отдельным протоколом с известным риском недоверенного snapshot; его нельзя использовать как edit command.

Память ledger ограничена 256 записями за hosting session; при заполнении новые ID отклоняются, существующие остаются доступными для сверки. Не удалять запись с известным ID ради места: такой eviction сделал бы повтор опасным. Reset/restart создаёт новую сессию и очищает память; команды предыдущей сессии получают `unknown/expired`, не повторяются автоматически. Текущее сохранение игры не содержит ledger и не обещает exactly-once между перезапусками; сохранённое клиентом намерение остаётся до явного разрешения. Replay с тем же ID, соединением и каноническим содержимым получает сохранённый результат; другая нагрузка с тем же ID — `collision` без изменения состояния; другой отправитель не узнаёт содержимое записи.

## Состояния и подтверждение

- `draft`: локальное намерение создано; перед отправкой его минимальные данные должны быть устойчиво записаны. Ошибка записи явно показывается и не выдаёт ложную гарантию.
- `pending`: запись передана или хост зарезервировал команду. Отправка и `accepted`/receipt — **не commit**. Запретить новый ход/вопрос на неподтверждённой базе.
- `committed`: только хостовый post-commit effect после проверки всех частей снимка фиксирует outcome в ledger; ответ содержит sessionId, commandId и revision результата. Клиент подтверждает только после commit подходящего snapshot, однозначно несущего этот receipt. Произвольный новый snapshot, похожий результат или ACK без commit не подтверждает команду.
- `rejected` / `conflict`: причина и актуальная база видимы; повтор с изменёнными предпосылками требует нового ID и явного решения пользователя. Старый ID никогда не переписывается.
- `delivery-unknown`: разрыв, потеря ACK/snapshot, restart или незавершённое применение; сохранить намерение и сверять тот же sessionId/commandId. Не повторять вслепую. Пока outcome не подтверждён, явная отмена ожидания не доказывает, что хост не применил команду.
- `cancelled`: разрешено только для несентого draft либо как явное локальное решение прекратить ожидание с предупреждением о неизвестном исходе; нельзя сообщать «не применено», если отправка могла произойти.

Повторный status request получает тот же ledger outcome, если сессия и связь авторства ещё доказуемы; при смене/утрате сессии — unknown. Удалять локальное намерение только после достоверного результата или явного решения пользователя. Последующие snapshots могут передавать сохранённые receipts для сверки; их принадлежность к сессии и revision и клиентский commit обязательны. Нет произвольного слияния inventory/history и автоматического replay.

## Совместимость и границы

Новая capability/version должна быть явно объявлена при соединении; если отсутствует или неизвестна, UI остаётся заблокированным и объясняет необходимость обновления обеих сторон. Существующий v1 turn stamp не является сам по себе объявлением поддержки edit protocol. До внедрения stage 3 никакие wire messages не отправляются. Component tests этапа 2 проверяют парсер, ledger и блокировку authority, но не являются доказательством реального React commit или доставки; те проверки обязательны на этапе 3 и 7.
