# Матрица инвентаря для аудита клиентских правок

Это детализация аудита этапа 1. Экспериментально включены сетевые команды собственной экипировки и ограниченные split/merge и перемещение в корневой контейнер через отдельные версии протокола; spectator и остальные действия player по-прежнему получают отказ; host/none используют существующие локальные правила. При вызове локального helper напрямую защиты сети нет. Решения о правах на NPC/хранилища не приняты. «Требуется» ниже — условие для проектирования команды, а не утверждение, что текущий код его соблюдает. Все команды также потребуют авторитетной сессии/ревизии, уникального operation ID, атомарности, результата после commit и обработки повтора/неизвестной доставки.

## Пути вызова

`useGameLogic` оборачивает `createInventoryActions` целиком в `guardGameplayActions`; `App.tsx` передаёт player/NPC операции в `InventoryScreen`, а тот — в `InventoryManagerUI`. В режиме NPC `onDropItem` означает передачу NPC→игроку, а не уничтожение; `onGiveItem` — обратную передачу. Stash и crafting идут через `App → SidePanel → StashView/CraftingScreen`, разбор — через `DetailRenderer → ItemDetailsRenderer`. `forgetHealedWound`, `forgetActiveWound`, `clearAllHealedWounds` дополнительно определены и **переопределяют одноимённые действия менеджера** в итоговом экспорте hook; для них проверять отдельные hook callbacks и UI ран, а не только обёрнутый менеджер. Открытие UI и просмотр изображений — презентация, не подтверждение правки.

## Поштучные операции

В строках ниже исходная локальная семантика; сетевое включение ограниченных equip/unequip, split/merge и move описано отдельно в конце. Остальные player-действия и spectator заблокированы. Дальнейшие предполагаемые права ниже требуют проверки на хосте, а не доверия параметру или UI. «Свой игрок» требует привязки соединения к единственному playerId; активный индекс и отображаемый объект могут различаться. Операции NPC не считаются разрешёнными игроку до определения полномочий.

| Entry point | Цель и стабильные идентификаторы / предполагаемые права | Текущий результат и обязательные конфликты для будущего контракта |
| --- | --- | --- |
| `equipItem` | Свой playerId + уникальный itemId и слот; первый кандидат команды. | Меняет слоты, `contentsPath`, характеристики/вес. UI проверяет слот; helper не проверяет владельца/слот/уникальность и отвергает только `0%`. Конфликты: предмет исчез/изменён, занят слот, двуручное оружие, повреждение, база/turn. |
| `unequipItem` | Свой playerId + уникальный itemId и ожидаемые слоты. | Очищает все слоты с ID и переносит предмет в корень; пересчёт. Конфликты: слот или предмет заменены, дубликат ID, двойное снятие. |
| `dropItem` | Свой playerId + itemId, уникальный в инвентаре и stash. | Переносит весь текущий объект в stash и снимает экипировку; отклоняет неоднозначный ID. Контейнерное содержимое/ссылки по именам ещё не разрешены; последующая очистка stash необратима. |
| `moveItem` | Свой playerId, itemId, destination containerId или корень. | Меняет путь и может снять экипировку; проверяются лишь некоторые вместимость/объём. Нужны запрет циклов и проверка содержимого/неоднозначных имён/ID, веса и конкурентного перемещения. |
| `splitItemStack` | Свой playerId, itemId, целое количество и новый ID на хосте. | Создаёт новый стек в корне, частично использованная единица остаётся в исходном; текущая локальная проверка не исключает все дробные/неконечные количества и специальные предметы. Конфликты: count/resource/ID/контейнер. |
| `mergeItemStacks` | Свой playerId, разные source/target itemId; перед удалением источника проверить полную совместимость. | Текущий helper сравнивает имя и часть полей, не все метаданные; потери свойств и особые предметы ещё не устранены. Требуется отказ, безопасная сумма count, проверка слотов и ресурса. |
| `disassembleItem` | Свой playerId + уникальный itemId и актуальная рецептура разбора. | Уменьшает стек на единицу, создаёт/сливает материалы, пересчитывает; локально доверяет `disassembleTo` из переданного объекта и сливает по имени. Нужны проверки рецепта, ID, экипировки, count, metadata и отсутствия частичного расхода. |
| `disassembleNpcItem` | NPCId + itemId, необходимые права на NPC. | Аналогичный разбор в NPC inventory; есть те же риски и отсутствует проверка полномочий. |
| `craftItem` | Рецепт и свой playerId; фактическое право/ресурсы определяет ГМ. | Возвращает строку `[System Action]`, `CraftingScreen` её игнорирует; расхода и результата нет. Не объявлять крафт рабочей командой. |
| `moveFromStashToInventory` | Свой playerId, уникальный itemId stash, положительное целое количество. | Локально переносит актуальные свойства, не сливает, сохраняет ID при полном переносе/создаёт новый при частичном; запрещает частичный sentient/container. Нужно решить вес содержимого контейнера, доступность stash и конфликты с очисткой. |
| `dropItemFromStash` | Свой playerId и однозначный stash itemId. | Удаляет записи по ID; необратимо, старый/повторный ID может удалить более одной записи. Требуются явное подтверждение и безопасный отказ при неоднозначности. |
| `handleTransferItem` | NPCId + source/target roles + itemId и количество, права обеих сторон. | Изменяет оба inventory и derived stats; helper ограничивает количество, не проверяет согласие и общий вес; UI проверяет вес NPC в одном направлении. Контейнеры, экипировка, sentient и legacy ID требуют отдельного контракта. |
| `handleEquipItemForNpc` | NPCId + itemId + слот и право на NPC. | Меняет NPC inventory/слоты и пересчитывает персонажей. NPC helper не проверяет прочность и пригодность слота. Нужны уникальность, совместимость и двухручность. |
| `handleUnequipItemForNpc` | NPCId + itemId, ожидаемые слоты, право на NPC. | Очищает слоты NPC и пересчитывает; конфликт при изменении владельца/предмета/слотов. |
| `handleMoveItemForNpc` | NPCId + itemId + containerId или корень, право на NPC. | Меняет путь и снимает экипировку; те же риски пути, циклов и вместимости, что для игрока. |
| `handleSplitItemForNpc` | NPCId + itemId + целое количество и право на NPC. | Локальные правила как у player split, включая незакрытые случаи количества и специальных предметов; новый ID должен быть создан хостом. |
| `handleMergeItemsForNpc` | NPCId + source/target itemId и право на NPC. | Локальные правила как у player merge, включая неполное сравнение метаданных и риск потери данных. |
| `forgetHealedWound` | PlayerId либо NPCId + woundId; административное право и правило истории. | Удаляет запись раны; отдельная hook-реализация обходит одноимённый менеджер. Зажившие раны должны сохранять историю; само отсутствие эффекта в `activePlayerEffects` не ошибка. Требуется отдельное решение о допустимости удаления. |
| `forgetActiveWound` | PlayerId либо NPCId + woundId; административное право. | Удаляет рану и эффекты, связанные через `sourceWoundId`; другие эффекты не трогать. Нужны защита от устаревшей раны и пересчёт. Отдельная hook-реализация. |
| `clearAllHealedWounds` | PlayerId либо NPCId + строгая база списка ран; административное право. | Фильтрует зажившие раны; отдельная hook-реализация. До согласования хранения истории и CAS не разрешать клиентам. |

Совпадение имён и наличие UI не доказывают безопасность helper, доступность владельца хосту, доставку или реальный multiplayer. Остальная матрица мира, истории и сетевых входов остаётся в [основном аудите](client-edit-operation-audit.md).

### Хостовый обработчик экипировки (этап 3, экспериментально включено)

`utils/clientEquipment.ts` строит кандидат только для уникального гостевого playerId на хосте в `FullParty`: проверяет целостность roster/inventory/занятых слотов, принадлежность и уникальность itemId, совместимость из текущего `equipmentSlot`, допустимые системные слоты, количество, прочность, двуручные руки и фактическую экипировку при снятии; затем использует существующие helper и пересчёт, не меняя исходный state или персонажа хоста. Сломанными также считаются варианты `0.0%` с пробелами. Вложенные/экипируемые контейнеры и `MultiplePersonalities` пока **отклоняются**, а не применяются с предположением о разделяемом инвентаре; некорректные legacy IDs/слоты и отсутствующие/нечисловые веса тоже приводят к отказу. Эти ограничения могут исключать часть существующих предметов и нуждаются в дальнейшем решении, а не означают поддержку всех случаев. `scripts/client-authoritative-equip.test.mjs` проверяет чистый reducer и локальный двухручный переход, но не сеть, commit, права по соединению или UI. Кандидат подключён к host edit dispatch; сквозные проверки и оставшиеся ограничения описаны в спецификации.


### Ограниченные split/merge (этап 5, экспериментально)

`utils/clientInventoryStack.ts` строит чистые host candidates для своего гостя в FullParty. Split принимает только безопасное целое количество, создаёт детерминированный ID из command UUID и проверяет коллизии во всём state; неполный ресурс остаётся в исходном стеке. Merge требует точного JSON-совпадения всех свойств, кроме ID/count, и полного ресурса. Обе операции консервативно отклоняют контейнеры, вложенные пути, экипируемые и sentient предметы, временные initialId, дубли и переполнение; если в инвентаре есть контейнеры/вложенные пути, пока отклоняется весь запрос. Unit тест `scripts/client-authoritative-stack.test.mjs` проверяет эти кандидаты и неизменность входа. Экспериментально подключены явные v2-команды с отдельной capability к тому же ledger, устойчивым намерениям и React commit barrier. `scripts/react-host-client-edit-loop.test.mjs` проверяет два production hook через искусственный транспорт, `scripts/browser-real-peer.mjs` — два вкладки headless Chromium с настоящим локальным PeerJS/WebRTC. Полный UI, все ошибки/гонки, отличающиеся браузерные профили и save/load stack после remote изменения ещё не доказаны; остальные операции остаются под guard.


### Ограниченное перемещение (этап 5, экспериментально)

Отдельная capability v3 позволяет перенести неэкипированный, не-sentient и не-контейнерный предмет своего guest между корнем и однозначным корневым контейнером (или между такими контейнерами) в `FullParty`. Хост проверяет ID по всему state, единственность имён контейнеров, одноуровневые пути, capacity/volume, целые количества, конечные веса и допустимое снижение веса, затем пересчитывает вес и характеристики. Контейнеры с одинаковыми именами, вложенные контейнеры/пути, equipped/sentient контейнеры и неоднозначные данные отклоняются. `scripts/client-authoritative-move.test.mjs` и `scripts/react-host-client-move-loop.test.mjs` проверяют reducer и пару production hooks через искусственный transport; дополнительно `scripts/browser-real-move.mjs` проверяет InventoryManagerUI в двух вкладках headless Chromium через синтетические DOM-события и локальный WebRTC; полный App и внешняя сеть не проверены. Остальные transfer/storage/world команды не включены.


### Подготовительный candidate stash — не включён

`utils/clientInventoryStash.ts` и `scripts/client-authoritative-stash.test.mjs` проверяют консервативный чистый candidate для root-предметов своего гостя в FullParty: host inventory/stash, уникальность ID, ресурс, полный/частичный стек, лимит веса, immutable результат. Контейнеры, sentient/экипированные предметы и сомнительные данные отклоняются. Команды ещё не подключены к сети или UI: требуется совместная проверка commit и rollback обоих объектов, ledger, прав, гонок и save/load.


Для equip/unequip дополнительно запрещены контейнеры или пути в инвентаре, sentient/temporary цель, неоднозначные глобальные ID, не-JSON metadata и переполнение веса: пересчёт сериализует персонажа и не должен молча менять нестандартные данные. Это консервативные ограничения, а не автоматическая миграция.
